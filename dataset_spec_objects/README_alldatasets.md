# AMADEUS Global + Dataset Catalog: current implementation

This README describes the current catalog contents verified from the local YAML files and active policies on **2026-11-10**. “Included” means a record is present in the catalog; it does not mean every value, decoder, access route or database operation is verified.

## Authoritative sources

- [global_catalog.yaml](../validated_catalog_handles/global_catalog.yaml) is authoritative for the assembled catalog records and global counts.
- The [dataset specification YAML files](../global_dataset_catalogs/) are authoritative for family membership, registered products, canonical definitions, native bindings and Assets. Their deduplicated union matches the global YAML exactly.
- The [discovery-handle YAML files](../validated_catalog_handles/) contain the same source/product/grid records as their matching full specifications. All 23 projections match.
- [policy.json](../catalog_gap_resolution/policy.json) supplies the current `mod13a2`, `gridmet_drought` and `pdsi_fix` settings. The active [integration marker](integration_20261107/active.json) and [inventory marker](inventory_extension_20261107/active.json) identify the enabled extension families; every listed family has a current specification and handle.
- The current full specifications are in `global_dataset_catalogs/`. The [catalog-first implementation record](../global_dataset_catalogs/catalog_implementation_20261110/README.md) documents the current bounded edits, phase gates and verification. Earlier overlay markers and `field_updates.json` are historical evidence; their replay scripts target the former specification location and must not be used to regenerate these revised profiles.
- [amadeus_schema.yaml](../amadeus_schema/src/amadeus_schema/schema/amadeus_schema.yaml), [amadeus_catalog.yaml](../amadeus_schema/src/amadeus_schema/schema/amadeus_catalog.yaml) and [amadeus_common.yaml](../amadeus_schema/src/amadeus_schema/schema/amadeus_common.yaml) define the container, catalog classes and shared vocabulary. The [validator’s DATASETS registry](../validated_catalog_handles/validate_catalogs.py) matches the 23 specification filenames.

Current YAML records determine actual membership and counts; active policies determine enabled selections. They take precedence over narrative documentation. No membership or policy conflict was found in this inspection. Workbooks, audit summaries and documentation are not used to override these current definitions.

### Included records with explicit qualifications

These qualifications describe current registered records, not completed remediation. The full specifications are authoritative for binding flags and notes; their source/product/grid projections match the existing `validated_catalog_handles/` YAMLs (the catalog-bundle directory in this checkout). A qualification does not remove a record from the catalog counts. Counts below explicitly distinguish Products, ProductVariables and grids; MODIS has separate rows for two different flags.

`ProductVariable.metadata_gaps` uses [MissingReasonEnum](../amadeus_schema/src/amadeus_schema/schema/amadeus_common.yaml): `under_investigation` means metadata interpretation needs investigation, while `available_but_not_extracted` identifies metadata not extracted into the profile. These are metadata flags, not observation QA states. A blank optional field, an empty enum list and an unresolved catalog-local CRS are distinct conditions; none is silently converted into an investigation flag. Rows stating **no binding flag** document issues in the existing descriptions/notes or implementation instead. Flags alone do not enforce runtime behavior; specific enforcement is identified where present.

The [mapping workbook](../catalog_schema_excel_mapping_with_unmapped.xlsx), worksheet `amadeus_catalog.yaml` rows 220/223/224 and worksheet `amadeus_common.yaml` row 47, mark `quality_flag_vocabulary`, `harmonization_note`, `metadata_gaps` and `MissingReasonEnum` as **No Match** to source Excel columns. Those flags cannot be populated by guessing from workbook blanks. Source sheet `Amadeus data sources` columns D/Q/W supply format assertions and E/S/X theme assertions; rows 23/24 say CSV, row 25 says ESRI ASCII Grid, row 26 includes Soil, and row 22 says Climate Regions. Those assertions need product-specific reconciliation with the YAML/native metadata and allowed enums. The [integration review](../catalog_dataset_integration.md#remaining-gaps-in-schema-coverage-and-recommended-placement) is guidance for proposed extensions; current [catalog slot definitions](../amadeus_schema/src/amadeus_schema/schema/amadeus_catalog.yaml) and [common enum definitions](../amadeus_schema/src/amadeus_schema/schema/amadeus_common.yaml) determine what is actually implemented. Recommendations below are proposed next steps, not changes already made.

The **Quick Wins / Easily Resolvable Issues** column selects two shared issues across all 23 families, ranked by implementation effort, evidence already available and low risk: **1 — the NEI/TRI generic-CSV vocabulary gap; 2 — the OLM/Ecoregion theme vocabulary gap**. Each is an additive metadata change using existing slots, with no access, decoding, aggregation or CRS behavior change. Other rows explain why their listed issues are not top-two selections; this is a qualitative prioritization, not a claim that no smaller subtask exists. These fixes are **proposed, not implemented**. After schema-extension approval, update affected mappings, audit/validation expectations and generation rules, regenerate the affected specifications/handles/global catalog/RDS, and validate schema conformance and unchanged scientific definitions. Resolving a vocabulary gap does not resolve the other qualifications in that row.
