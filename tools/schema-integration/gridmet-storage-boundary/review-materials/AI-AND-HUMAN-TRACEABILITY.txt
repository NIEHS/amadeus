AI ASSISTANCE, HUMAN DECISIONS AND DETERMINISTIC ENFORCEMENT
Documentation revision: 12 November 2026. Review copy; no runtime/code/repository change or push.

POLICY
Use AI assistance for development, test design, review and documentation. Trace every maintained rule to its authority, implementation, test evidence and human approval status. Humans establish unit authority, temporal meaning, request-to-result binding, provenance truth and acceptance policies. AI suggestions, deterministic test results and human decisions are distinct evidence types. No live AI model is used to decide acceptance in this implementation.

HOW THE FLOW WORKS
1. Humans select authoritative metadata and scientific policy. AI may propose mappings; it cannot establish authority by generating plausible text.
2. LinkML and build QA compile versioned contracts/catalog/SQL. Code generation is deterministic; correct generation does not establish correct scientific definitions. Successful build status is separate from scientific approval.
3. Users provide ordinary Amadeus variables, dates, sites and scientific arguments. Existing Amadeus checks and science remain unchanged. The optional explicit recorder observes calls/sources/outputs alongside execution; Amadeus does not depend on it.
4. After calculate returns, export consumes actual results and recorded context. Deterministic R, JSON Schema and SQL enforce the scoped contract. The pilot example_gridmet.R orchestration and schema_validator.R checks are not used by this current architecture. Existing Amadeus internal checks remain.
5. Parquet typing and full-column readback support storage fidelity. They cannot alone establish scientific units, physical time, completeness or true history. SQL and shared boundary checks still execute automatically after calculation.
6. DuckDB load, integrity/fidelity/reopen checks precede completed publication. File manifests bind owned outputs/receipts. Saved query checks bytes and bindings at open; raw sources are not reread. Read-only bits and unsigned hashes are not production immutability/authentication.
7. Humans review evidence, resolve scientific questions, qualify independent environments and approve a bounded release. Machine acceptance is not human approval; scientific sign-off and independent replay remain pending.

RULE CHANGE PROCEDURE
Assign a stable rule ID. Record the source/version/hash and why it is authoritative. Distinguish observed source facts from approved policy and assumptions. Identify code/SQL/contract location and exact supported dataset/method scope. Record AI assistance (tool/model/version/date when actually known, prompt or artifact reference where appropriate), human edits and review. Unknown attribution stays unknown.
Add a valid control, a minimally invalid case expected to fail and relevant edge cases; retain observed outcomes and exact code/input/release identities. Identify evidence as current versus historical and direct rule-level versus suite-level. Human reviewer records name/date/decision/rationale and approved scope/hash. On changes, rebuild affected artifacts, rerun affected tests and invalidate prior approval for changed semantics. Preserve earlier versions and unresolved issues. This is a proposed maintenance procedure documented here, not a newly implemented approval service or automatic runtime blocker.
